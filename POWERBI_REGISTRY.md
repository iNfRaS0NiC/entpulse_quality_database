# PowerBI DQ Registry

## Purpose

This file is the compact source of truth for assigned PowerBI DQ CheckIDs, their
classification, approval status and SQL location.

Full SQL never belongs here. It is stored in one sport-scoped file under
`POWERBI_QUERIES/`.

## Registry rules

- Keep exactly one row per assigned CheckID.
- Sort rows by Sport and then by CheckID.
- DQ numbering starts at `DQ-001` independently for each sport.
- Assign an ID only after the user approves the concrete check.
- An assigned CheckID is never renumbered, deleted or reused. A deprecated check keeps its
  row and its ID: set `Status` to `Deprecated` and, when the executable SQL was
  intentionally removed, `Query file` to `—`. The ID stays permanently reserved, so
  CheckIDs are stable identifiers for PowerBI and any external report and may contain
  gaps. `POWERBI.md` owns this rule.
- Use `Approved` for an active approved query.
- `Family` names the logical check: a `GLOBAL-DQ-NNN` template ID, or `—` when no template
  expresses it. It is the key that groups one check across sports, whose own CheckIDs differ
  because numbering restarts per sport.
- `Category` identifies the DQ problem family.
- `Object` identifies the canonical object or logical storage layer checked.
- `Name` must match the `-- Name - ...` line in the SQL exactly, or the template's `Name`
  when the row runs a template.
- An `Approved` row's `Query file` points either to a `GLOBAL_DQ/` template, meaning the row
  is an instantiation with no per-sport statement, or to the one per-sport SQL file
  containing the full active query. Never both. `POWERBI.md` owns this rule.
- Insert new approved rows immediately before the exact registry marker. Never place a
  row after, move or delete the marker. Replace an existing CheckID row in place.
