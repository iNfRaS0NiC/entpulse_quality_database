# GLOBAL DQ Template Registry

## Purpose

A GLOBAL DQ template is one approved data-quality check whose logic holds for every
applicable sport, stored once and executed for a selected sport by substituting its
declared parameters. It carries the full `POWERBI.md` contract — identity header,
findings-plus-coverage, audited-object granularity, commented scope filter — and differs
from a sport check only in that its sport-specific values are parameters instead of
literals.

This exists because the alternative does not scale. A hand-copied sport file is ~60 lines
per check; at 110 sports one logic fix would have to be applied 110 times, with nothing
detecting the copies that drifted. A template is fixed once and every sport that
instantiates it follows.

`GLOBAL_QUERIES/` answers *what is stored*. `GLOBAL_DQ/` asserts *what is wrong*. The
boundary between discovery and DQ is unchanged and owned by `POWERBI.md`.

## What is still not automatic

A template is not permission to check a sport. The authorization gate in `POWERBI.md`
applies unchanged: DQ work starts only after the user names a sport and a category, and a
check is instantiated for that sport only after the user approves it.

What changes is what approval produces. Instead of a new ~60-line statement, it produces:

1. one row in `POWERBI_REGISTRY.md` whose `Family` column names the template;
2. the parameter values for that sport in `SPORTS/params.json`, if not already recorded.

No per-sport copy of the SQL is created. A check that genuinely cannot be expressed
through declared parameters stays sport-authored, with `Family` = `—` and its statement in
`POWERBI_QUERIES/<SportSlug>.sql`.

## Parameter contract

Mandatory parameters use the same uppercase double-brace tokens as `GLOBAL_QUERIES/`, and
`WORKFLOW.md` owns the general rule. Two kinds occur:

| Kind | Substitution | Example |
|---|---|---|
| Scalar | A numeric or quoted value in a comparison | `{{SPORT_ID}}`, `{{STATISTIC_TYPE_ID}}` |
| Physical name fragment | Text inside a table or column name | `statistic_participants{{SHARD_ID}}` |
| List | A quoted, comma-separated list inside `IN (...)` | `{{EVENT_PARTICIPANT_TYPE_LIST}}` |

A list parameter's value already contains its quotes: `'athlete'` or `'athlete', 'team'`.
It is a SQL fragment, so it is only ever filled from `SPORTS/params.json`, never from
user-supplied text.

| Parameter | Meaning |
|---|---|
| `{{SPORT_ID}}` | Confirmed numeric `sport.id` |
| `{{EVENT_PARTICIPANT_TYPE_LIST}}` | Participant types the sport uses in `event_participants` |
| `{{REGISTRY_PARTICIPANT_TYPE_LIST}}` | Participant types present in the sport's `object_participants` registry |
| `{{STATISTIC_TYPE_ID}}` | Confirmed `statistic.statistic_typeFK` |
| `{{SHARD_ID}}` | Confirmed physical statistic participant/data shard number |
| `{{DATA_RANK_TYPE_ID}}` | `statistic_data_type.id` of the Rank data field for that statistic type |
| `{{CONFIG_START_DATE_TYPE_ID}}` | `statistic_data_type.id` of the Start date config field |
| `{{CONFIG_END_DATE_TYPE_ID}}` | `statistic_data_type.id` of the End date config field |
| `{{CONFIG_EVENT_ID_TYPE_ID}}` | `statistic_data_type.id` of the Event id config field |
| `{{DATA_COMMENT_TYPE_ID}}` | `statistic_data_type.id` of the Comment data field |
| `{{DATA_MEDAL_TYPE_ID}}` | `statistic_data_type.id` of the Medal data field |
| `{{DATA_TIME_TYPE_ID}}` | `statistic_data_type.id` of the current Time data field |
| `{{DATA_TIME_DIFFERENCE_TYPE_ID}}` | `statistic_data_type.id` of the Time Difference data field |
| `{{DATA_DEPRECATED_DURATION_TYPE_ID}}` | `statistic_data_type.id` of the superseded Duration data field |
| `{{RESULT_RANK_TYPE_ID}}` | `result_type.id` of the sport's Rank event result |
| `{{RESULT_COMMENT_TYPE_ID}}` | `result_type.id` of the sport's Comment event result |
| `{{RESULT_MEDAL_TYPE_ID}}` | `result_type.id` of the sport's Medal event result |
| `{{RESULT_DURATION_TYPE_ID}}` | `result_type.id` of the sport's leader/gap Duration event result |
| `{{CONFIG_GENDER_TYPE_ID}}` | `statistic_data_type.id` of the Gender config field |
| `{{FINAL_ROUND_TYPE_LIST}}` | Comma-separated `round_type.id` values the sport treats as its decisive Final round |
| `{{DUPLICATE_KEY_INCLUDES_EVENT_NAME}}` | `1` where the sport's event name carries information beyond which competitors take part, so two events sharing a slot and a participant set are told apart by it; `0` where the name is built from the participants themselves and therefore adds nothing but an arbitrary ordering. A heats-based sport records 1, because Moto 1 and Moto 2 are distinguished by name alone. A sport that instantiates `GLOBAL-DQ-096` records 0 by definition: that check asserts the name is made of the participants |
| `{{ELIMINATION_ROUND_NAME_LIST}}` | A quoted, comma-separated list of lower-case `round_type.name` values naming a round in which some entries go out and the rest go on, so the round is a knockout by definition |
| `{{GROUP_ROUND_NAME_LIST}}` | A quoted, comma-separated list of lower-case `round_type.name` values naming a round nobody is eliminated in, so the round is not a knockout. A name the sport cannot classify from its name alone - a placement or qualification round whose answer depends on the format - belongs in neither list and is left unjudged |
| `{{DUPLICATE_KEY_USES_CALENDAR_DAY}}` | `1` where one meeting between the same competitors happens at most once a day, so two of them on one date are a duplicate whatever their kick-off; `0` where the sport re-runs the same field several times in a day - motos, rounds of one heat series - and only the exact moment separates them. A sport recording 1 catches the re-import that arrived with a shifted kick-off; a sport recording 0 would report its whole heat structure |
| `{{BRONZE_ROUND_TYPE_LIST}}` | Comma-separated `round_type.id` values of the match that decides bronze, where the sport decides it outside the Final. Together with `FINAL_ROUND_TYPE_LIST` it says which medal each round awards, which a single medal-round list cannot: the Final decides gold and silver, the bronze match decides bronze. A sport awarding every medal in one event records a value that never occurs, such as `0` |
| `{{MEDAL_ROUND_TYPE_LIST}}` | Comma-separated `round_type.id` values on which the sport awards a medal at all. It is a superset of `FINAL_ROUND_TYPE_LIST` wherever a medal is decided outside the Final: a head-to-head sport settles bronze in its own match, so that round belongs here and the Final alone does not describe where medals occur. A sport awarding every medal in one event records the same values in both |
| `{{RANK_MAX_PLAUSIBLE}}` | Highest rank value the sport can legitimately award in one event |
| `{{NOT_STARTED_DESC_LIST}}` | Comma-separated `status_descFK` values under `status_type='notstarted'` that the sport expects to carry no results |
| `{{TIMED_DISCIPLINE_LIST}}` | Comma-separated `discipline.id` values in which the sport records a measured time; judged disciplines are excluded |
| `{{RESULT_FULL_TIME_TYPE_ID}}` | `result_type.id` of the sport's absolute full-time event result |
| `{{STALE_NOT_STARTED_DAYS}}` | Days after its start date beyond which the sport treats a still not-started event as stale |
| `{{PLACEHOLDER_COUNTRY_LIST}}` | A quoted, comma-separated list of `country.name` values the sport treats as a placeholder rather than a real country |
| `{{DATA_TEAM_TYPE_ID}}` | `statistic_data_type.id` of the Team data field, which holds the `participant.id` of the team an athlete competes for inside the statistic |
| `{{ROUND_TYPE_LIST}}` | Comma-separated `round_type.id` values the sport is confirmed to contest |
| `{{SCOPE_TYPE_ID}}` | One confirmed `scope_type.id` used by templates whose semantic rule applies to a single container type |
| `{{SCOPE_TYPE_LIST}}` | Comma-separated active `scope_type.id` values used by a relational check that must audit every confirmed scope container type |
| `{{NUMERIC_RESULT_TYPE_LIST}}` | Comma-separated `result_type.id` values that carry a measured quantity rather than text or a time |
| `{{NUMERIC_DATA_TYPE_LIST}}` | Comma-separated `statistic_data_type.id` values that carry a measured quantity rather than text or a time |
| `{{RESULT_COMMENT_VALUE_LIST}}` | A quoted, comma-separated list of the Comment result status codes the sport is confirmed to use |
| `{{DATA_COMMENT_VALUE_LIST}}` | A quoted, comma-separated list of the Comment data status codes the sport is confirmed to use |
| `{{SERIES_MIN_YEARS}}` | Fewest editions a template must hold before its rhythm is trusted and a break in it is reported; three is the fewest that yields two intervals |
| `{{SERIES_SKIP_YEARS}}` | Comma-separated calendar years in which the sport did not run, so they are neither editions nor breaks; a sport with nothing to skip records a year that never occurs, such as `0` |

Every value is a confirmed structural fact recorded in the sport's file before it reaches
`SPORTS/params.json`. A parameter that is not yet confirmed for a sport means the template
cannot be instantiated for it yet — not that a plausible value may be guessed.

## Sport parameter file

`SPORTS/params.json` maps a sport slug to its confirmed values:

```json
{
  "BMX": {
    "SPORT_ID": 58,
    "EVENT_PARTICIPANT_TYPE_LIST": "'athlete'",
    "REGISTRY_PARTICIPANT_TYPE_LIST": "'athlete', 'team'",
    "STATISTIC_TYPE_ID": 11,
    "SHARD_ID": 11
  }
}
```

`TOOLS/Run-Query.ps1 -Sport <name>` reads it before querying the database, so a recorded
value is preferred over a discovered one: the file holds evidence, discovery holds a
heuristic. An explicit `-SportId` or `-Params` still overrides both.

The file is data, not documentation. The narrative evidence for each value stays in
`SPORTS/<SportSlug>.md`; `TOOLS/Test-Package.ps1` checks that the two agree on `SPORT_ID`.

## Qualification rule

A check qualifies as a GLOBAL DQ template only when:

- its relation path is supported by `DATABASE.md`;
- the violation it asserts is wrong in every applicable sport, not only in the sport it was
  first written for;
- every sport-varying input is a declared parameter;
- it contains no hard-coded sport ID or sport name;
- its applicability prerequisite is stated, so a sport where the condition is legitimately
  absent is excluded rather than reported as violating;
- one CheckID identifies exactly one executable statement.

The last point matters most in practice. "Every stage has an age class" is true for some
sports and meaningless for others; such a check is global only because the prerequisite
column says where it applies.

**"Legitimately absent" means structurally absent, and is never read off a row count.** The
prerequisite column describes what a sport *stores* — which columns, layers and relations its
records use — not how many rows currently carry a given value. A sport whose events hold a
status column satisfies the prerequisite of a status rule even while no event carries that
status today; excluding it on that count silently disables the rule for the day the first
such row arrives, which is the day it was written for. The same applies to a value list, a
type or a discipline that happens to be unused this month. Where the two are hard to tell
apart, ask before classifying. `TOOLS/README.md` owns the same distinction for `_checkSignal`
and `WORKFLOW.md` states it for scope.

## Promoting a sport check to a template

Only after explicit user approval:

1. prove the violation condition is not sport-specific;
2. replace every sport literal with a declared parameter;
3. state the applicability prerequisite;
4. assign the next unused `GLOBAL-DQ-NNN`;
5. insert the statement in its domain file by CheckID order;
6. insert the registry row immediately before the marker above;
7. set the originating sport's registry `Family` to the new template ID;
8. run `TOOLS/Test-Package.ps1`.

A sport check keeps its own CheckID after promotion. `Family` records that the two are the
same logical check; the sport CheckID is never renumbered or reused.

## When not to make a check global

A template that fits every sport is worth having. A template stretched until it fits every
sport is not, and the difference is visible in the parameter list: each new flag added to
keep one more sport inside a shared statement is a place where the next reader has to work
out which sport the branch was for.

**Several narrower checks that work beat one wide check that has to be configured into
correctness.** A sport whose competition model genuinely differs is better served by its own
statement than by a parameter that switches the shared one's meaning.

The clearest line is the competition model `DATABASE.md` `DB-SEM-015` records:

- in a **head-to-head team sport** the same two sides do not meet twice inside a few hours,
  every event holds exactly two entries, and a result is read as a pair;
- in a **listing sport** the same field is entered several times in a day by design - motos,
  heats, runs - every event holds many entries, and a result is read against the field.

An assertion that is obviously true in one of those is often meaningless or actively wrong in
the other, and no parameter repairs that: it only hides which case the reader is in.
`GLOBAL-DQ-062` is the worked example. Whether two events sharing a day and a participant set
are a duplicate has opposite answers in the two models, and it needed two declared facts -
`DUPLICATE_KEY_USES_CALENDAR_DAY` and `DUPLICATE_KEY_INCLUDES_EVENT_NAME` - to stay one
statement. That was still worth it there, because the two facts are small and orthogonal and
the finding is the same defect either way. A third flag would not have been.

Two consequences for practice:

- when a template needs a new parameter only so that one sport stops being reported, ask
  first whether that sport should have its own statement instead;
- **a change to a shared template is measured against every sport that instantiates it,
  before it is kept.** Running it only for the sport in hand is how a silent regression
  reaches the sports nobody was looking at.
